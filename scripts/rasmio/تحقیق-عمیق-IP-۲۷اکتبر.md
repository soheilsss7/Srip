# تحقیق عمیق دربارهٔ تأمین IP خروجی برای ربات

تاریخ: ۲۷ اکتبر ۲۰۲۶ — موجودی فهرست‌ها در ۰۶:۵۶:۲۲ تهران ثبت شد.

## نتیجهٔ اجرایی

**مسیرهای واقعی برای تغییر IP وجود دارند؛ اما منبعِ تأییدشدهٔ «رایگان، نامحدود، همیشه استفاده‌نشده برای رسمیو» پیدا نشد.** بهترین نامزدِ آزمایش بدون خرید اشتراک، یک مخزن پراکسی با بررسی زندهٔ خروجی و کیفیت داده است، نه اجرای کورکورانهٔ یک لیست. IPv6 مسیر دوم و مشروط است. سرویس ابری و مسکونی هم بررسی شدند، ولی رایگانِ دائمی/نامحدود محسوب نمی‌شوند.

این تحقیق مشکل را «حل‌شده» اعلام نمی‌کند: هیچ پراکسی عمومی نصب یا به ربات تولیدی وصل نشده و هیچ شرکت از طریق نامزدهای این تحقیق دریافت نشده است.

## دامنه و روش بررسی

- ۷ جست‌وجوی وب با عمق ۳: مخزن‌های پراکسی، خروجی ابری، Tor، IPv6، Cloudflare، قیمت جدید AWS و محدودیت‌های GitHub.
- ۶ جست‌وجوی مستقیم API گیت‌هاب؛ ۱۰۶ نتیجه با **۹۹ مخزن یکتا**. عنوان/توضیح نتایج مرور شد، نه اینکه کد هر ۹۹ مخزن ممیزی شده باشد.
- README و وضعیت مخزنِ **۱۶ پروژه** مستقیماً از GitHub خوانده شد.
- ۶ فایل فهرست از ۴ مخزن دانلود، قالب ورودی‌ها و عمومی‌بودن آدرس‌ها بررسی و تکراری‌ها حذف شد؛ commit مرجع و SHA-256 هر فایل در JSON شواهد ثبت شد.
- هیچ ادعایی دربارهٔ جست‌وجوی تمام گیت‌هاب، ممیزی امنیتی کامل پروژه‌ها یا تست زندهٔ پراکسی‌ها ندارم.

شواهد: `IP-ROTATION-RESEARCH-2026-10-27.json`.

## گزینه‌ها و تصمیم فنی

### ۱. مخزن پراکسی عمومی + کنترل سلامت: نامزد آزمایش رایگان

ابزارهای [mubeng](https://github.com/mubeng/mubeng)، [rota](https://github.com/alpkeskin/rota) و [proxy_pool](https://github.com/jhao104/proxy_pool) برای چرخش و بررسی پراکسی هستند؛ خودشان مالک مخزن نامحدود IP نیستند. mubeng چرخش پس از N درخواست و بررسی سلامت دارد. مستنداتش هشدار می‌دهد که در حالت ناهمزمان، مرز دقیق N درخواست تضمین نمی‌شود و برای رفتار ترتیبی به حالت sync نیاز است. rota مخزن، health check و حالت sticky با N درخواست دارد. [9](https://github.com/mubeng/mubeng) [1](https://github.com/alpkeskin/rota)

**تصمیم:** برای آزمایش کوچکِ بدون خرید اشتراک قابل بررسی است، ولی فقط روی سرورهایی که استفاده از آن‌ها مجاز است. سرعت، uptime، TLS سالم، IP خروجی مستقل و پذیرفته‌شدن توسط رسمیو باید جداگانه اثبات شوند. درج در یک مخزن عمومی، مجوز استفاده از یک سرور ناشناس نیست. هیچ کد ناشناسی از این پروژه‌ها اجرا نکردم.

### ۲. AWS API Gateway / FireProx / requests-ip-rotator: خروجی واقعی، نه بی‌نهایت

FireProx و requests-ip-rotator از خروجی API Gateway استفاده می‌کنند. README ابزار دوم می‌گوید هدرهای AWS می‌توانند باعث شناسایی و مسدودشدن شوند؛ عبارت «pseudo-infinite» تضمین عدم تکرار نیست. IPSpinner صریحاً محدودبودن مجموعهٔ IP هر منطقه و تمام‌شدن آدرس‌های تازه را توضیح می‌دهد. [1](https://github.com/ustayready/fireprox) [3](https://github.com/Ge0rg3/requests-ip-rotator) [8](https://github.com/synacktiv/IPSpinner)

README قدیمیِ requests-ip-rotator ادعای یک میلیون درخواست رایگان در هر منطقه دارد؛ **آن را مبنای بودجه قرار ندهیم**. مستندات رسمی فعلی AWS برای حساب جدید، اعتبار اولیه و طرح آزمایشی حداکثر شش‌ماهه/تا اتمام اعتبار را توضیح می‌دهد؛ روی Paid، پس از اعتبار هزینه ایجاد می‌شود. قیمت API Gateway علاوه بر فراخوانی، انتقال دادهٔ خروجی را هم در نظر می‌گیرد. [26](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/free-tier.html) [1](https://aws.amazon.com/api-gateway/pricing/)

**تصمیم:** نامزدِ مشروط به حساب ابری مجاز و سقف هزینه، نه راه‌حلِ منطبق با شرط رایگانِ دائمی. هیچ حساب، کلید یا منبع ابری ساخته نشد. ابزار Python هم جایگزین مستقیم fetch و Puppeteer فعلی نیست.

### ۳. Cloudflare Workers / FlareProx: سهمیهٔ درخواست با سهمیهٔ IP فرق دارد

FlareProx پراکسیِ مبتنی بر Workers می‌سازد. پلن رایگان Workers طبق مستندات رسمی، ۱۰۰هزار درخواست در روز دارد؛ این عدد **تعداد IP تازه نیست**. [17](https://github.com/MrTurvey/flareprox) [1](https://developers.cloudflare.com/workers/platform/limits/)

در بررسی مستندات، تضمین «IP استفاده‌نشده برای هر چهار درخواست» پیدا نکردم. گزارش یک پروژه دربارهٔ ntfy هم نمونه‌ای از تمام‌شدن سهمیهٔ یک سایت به‌علت خروجی مشترک Workers است؛ این گزارش مربوط به ntfy است و نتیجهٔ آزمایش رسمیو نیست. [22](https://github.com/binwiederhier/ntfy/issues/1963)

**تصمیم:** ساخت چند Worker مساوی ساخت چند IP مستقل نیست؛ برای خواستهٔ سخت‌گیرانهٔ این پروژه گزینهٔ تضمینی نیست. به استقرار یا اتصال Arena به deploy دست نزدم.

### ۴. Tor: بدون خرید IP، اما مجموعهٔ خروجی محدود

TorIpChanger توضیح می‌دهد مدار جدید الزاماً IP جدید نیست. پروژهٔ TorRotatingHttpProxy تاریخچهٔ خروجی و کنترل عدم تکرار دارد، ولی خودش تصریح می‌کند با الزام یکتایی دائمی ممکن است خروجی آماده تمام شود و 503 بدهد. این پروژه در بررسی API فقط صفر ستاره داشت؛ انتخاب اول برای اجرای تولیدی نیست. [28](https://github.com/DusanMadar/TorIpChanger) [1](https://github.com/bariskisir/TorRotatingHttpProxy)

**تصمیم:** جایگزین «IP نامحدود» نیست؛ NEWNYM نباید بدون سنجش IP موفق حساب شود. موفقیت Tor روی رسمیو تست نشده است. افزایش بی‌رویهٔ مدارها را راه‌حل این ربات پیشنهاد نمی‌کنم.

### ۵. IPv6 از یک subnet مسیریابی‌شده: نزدیک‌ترین گزینه به تعداد بسیار زیاد، اما مشروط

پروژهٔ zu1k/http-proxy-ipv6-pool به subnet واقعاً routed روی سرور نیاز دارد؛ اضافه‌کردن رشته‌های IPv6 به تنظیمات، مالکیت یا مسیر شبکه ایجاد نمی‌کند. ابزارهای IPv6-only نیز برای مقصد بدون IPv6 راه چرخش IPv6 ندارند. [4](https://github.com/zu1k/http-proxy-ipv6-pool) [7](https://github.com/muxover/vanta)

**تصمیم:** فقط اگر سرورِ در اختیار، prefix قابل‌استفاده داشته باشد و رسمیو از همان مسیر واقعاً با IPv6 قابل دسترسی باشد ارزش آزمایش دارد. پشتیبانی IPv6 رسمیو در این تحقیق تست نشده است. حتی با /64، ممکن است محدودیت سایت بر مبنای prefix یا عوامل دیگر باشد؛ تعداد آدرس زیاد تضمین پذیرش نیست. بدون دست‌زدن به Plesk یا شبکهٔ فعلی، این گزینه صرفاً مشروط باقی مانده است.

### ۶. IPSpinner و اجرای فراوان GitHub Actions: مشکل را به زیرساخت دیگری منتقل می‌کند

IPSpinner از AWS، Azure Cloud Shell و GitHub Actions پشتیبانی می‌کند، اما برای Actions خودش دربارهٔ خطر بسته‌شدن حساب هشدار می‌دهد. اعداد موجودی IP و نرخ ابزار، اندازه‌گیری قدیمی خود پروژه‌اند، نه سهمیهٔ فعلی حساب ما. استفاده از حساب‌های دورریختنی/تکثیر حساب یا مصرف بی‌رویهٔ سرویس رایگان پیشنهاد نمی‌شود. [8](https://github.com/synacktiv/IPSpinner)

مستندات GitHub هم IP رانرها را پویا و از زیرساخت مشترک توصیف می‌کند؛ IP متفاوتِ job، اثبات «استفاده‌نشده برای رسمیو» نیست. [2](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-githubs-ip-addresses)

**تصمیم:** این گزینه منبع نامحدود و تضمینی نیست؛ زنجیرهٔ فعلی را صرفاً برای شکار IP به صدها اجرای همزمان تبدیل نکردم.

### ۷. سرویس مسکونی تجاری: گزینهٔ پولی، خارج از قید فعلی

مستندات Oxylabs از مخزن IP و rotation/sticky session و احراز هویت سرویس صحبت می‌کند؛ این یک سرویسِ تأمین IP است، نه صرفاً برنامهٔ مدیریت لیست. داشتن مخزن بزرگ همچنان به معنی سهمیهٔ نامحدود یا IP استفاده‌نشده در مقصد نیست. [20](https://github.com/oxylabs/residential-proxies)

**تصمیم:** فقط در صورت تغییر صریح شرط رایگان مطرح می‌شود؛ خرید، ثبت‌نام، trial یا اتصال خودکار انجام نشد.

## اندازهٔ مسئله: چرا هر لیست بزرگی کافی نیست؟

محاسبات زیر **مشروط** به فرض کاربر است: هر IP بتواند دقیقاً چهار صفحهٔ شرکتِ موفق بدهد؛ شکست و درخواست اضافه صفر باشد.

- ۹ شرکت در دقیقه، دست‌کم ۲٫۲۵ سهمیهٔ IP در دقیقه یا ۳٬۲۴۰ سهمیه در روز می‌خواهد.
- اگر محدودیت هر IP واقعاً چهار روز باشد، حفظ همین نرخ به حداقل ۱۲٬۹۶۰ سهمیهٔ IP مستقل در آن پنجره نیاز دارد.
- برای ۳۱۹٬۵۶۱ شرکتِ فاقد فایل جزئیات در snapshot اخیر، حدود ۷۹٬۸۹۱ بستهٔ چهارصفحه‌ای لازم است؛ این عدد «IP یکتای همیشگی» نیست، چون بازگشت سهمیه با گذر زمان ممکن است.

این‌ها حداقل نظری‌اند، نه عملکرد اندازه‌گیری‌شده. ۱۰٬۶۵۷ آدرس سرورِ لیست رایگان، حتی قبل از آزمون سلامت و خروجی، با تضمین چنین ظرفیتی یکی نیست. افراد دیگر هم می‌توانند همان IPها را استفاده کرده باشند.

## ناسازگاری مهم با ربات فعلی

بررسی کد همین مخزن نشان داد ربات هم از fetch در Node و هم از Puppeteer استفاده می‌کند. تغییر پراکسیِ یکی، دیگری را جابه‌جا نمی‌کند. network-audit فعلی هم ابزار مشاهده است، نه ابزار تغییر مسیر.

در هر آزمایش بعدی باید:
1. ترافیک fetch، مرورگر و سنجش IP از همان مسیر کنترل‌شده عبور کنند؛ صرف افزودن یک متغیر محیطی اثبات تغییر مسیر نیست.
2. خروجی‌ها بر اساس **IP مشاهده‌شدهٔ خروجی** حذف تکرار شوند، نه فقط host:port.
3. سقف چهار صفحه با رزرو سهمیهٔ اتمی میان workerها کنترل شود؛ تعداد اتصال CONNECT یا درخواست به سرویس سنجش IP، معادل تعداد صفحات شرکت نیست.
4. keep-alive، ریدایرکت، reload و درخواست‌های HTML اضافی حساب شوند؛ عوض‌شدن انتخاب پراکسی نباید اتصال باز قبلی را حفظ کند.
5. تاریخچه میان jobها باقی بماند؛ اجرای جدید شمارنده را به‌دروغ صفر نکند.
6. در خرابی پراکسی، بازگشت مستقیم پنهانی ممنوع باشد؛ بررسی TLS غیرفعال نشود؛ کوکی حساب، کلید GitHub و اسرار از مسیر عمومی عبور نکنند.
7. IP مشاهده‌شده توسط یک سرویس echo همچنان لزوماً IP دیده‌شده در مقصد دیگر نیست؛ موفقیتِ فایل شرکت باید جداگانه کنترل شود.
8. پاسخ محدود/خالی در صف بماند، فایل سالم قبلی حفظ شود و دادهٔ غیرخالی با کامل‌بودن پروفایل اشتباه نشود.

## آزمایش تصمیم‌ساز پیشنهادی، پیش از اتصال تولیدی

**نامزد اول:** تعداد کمی خروجیِ مجاز از منابع رایگانِ به‌روز + بررسی مستقل، با یک مدیر پراکسی ساده؛ mubeng گزینهٔ کم‌پیچیدگی‌تری برای شروع تحقیق است، نه انتخاب امنیتیِ تأییدشدهٔ نهایی.

آزمایش محدود: حداکثر ۲۰ نامزد، timeout و تعداد تلاش محدود، بررسی HTTPS و IP خروجی، سپس یک صفحهٔ شرکت در هر خروجیِ پذیرفته‌شده. فقط با خروجی‌های مجاز و بدون حساب/کوکی/اسرار. مرحلهٔ اول نباید اسکن وسیع سرورهای ناشناس باشد.

**معیار ورود به تولید:** دست‌کم ۵ خروجی مستقلِ مشاهده‌شده و ۲۰ فایل شرکتِ غیرخالی، حفظ دادهٔ قبلی، نبود نشت مسیر مستقیم، ثبت علت شکست و نرخ واقعی شرکت/دقیقه. حتی این آزمایش فقط امکان‌پذیری محدود را نشان می‌دهد، نه تضمین بی‌نهایت IP یا کامل‌بودن همهٔ پروفایل‌ها. تستِ بخش‌ها و صفحه‌بندی جداگانه لازم است.

این آزمایش زنده انجام نشده است: محیط فعلی امکان اتصال آزاد به آدرس‌های پراکسی عمومی و مقصد را ندارد. از ارسال workflow یا سرویس واسط برای دورزدن محدودیت شبکهٔ این محیط استفاده نکردم. ابزار ناشناس و تأییدنشده را هم روی رباتِ دارای دسترسی گیت‌هاب نصب نکردم.

## جمع‌بندی وضعیت

- **پیدا شد:** ابزارها و منابع واقعی برای ساخت یک مخزن خروجی محدود و قابل‌آزمایش؛ موجودی شمارش‌شده و پروژه‌های جایگزین.
- **پیدا نشد:** تضمین رایگانِ دائمی و نامحدود برای IP استفاده‌نشده در رسمیو.
- **انجام شد:** تحقیق عمق ۳، جست‌وجوی API، خواندن مستندات اولیه، شمارش فایل‌ها و تحلیل اتصال به ربات.
- **انجام نشد:** تست زندهٔ پراکسی، دریافت شرکت با این منابع، نصب تولیدی، ساخت حساب یا منابع ابری، تغییر workflow فعال یا دست‌زدن به deploy/Plesk.
