## ۲) سیاست‌های حاکم بر این برنامه (سه تصمیم)

۱) **هیچ ماژول ساخته‌شده حذف نمی‌شود.** آنچه v14 از سند حذف کرده (فصل ۱۹.۴/۱۹.۵ اصالت و حاکمیت AI، فرم F13 اصالت، فرم F17 ریسک AI، پروژه‌های P13/P17 قدیم، اصل ششم «نظارت انسانی»، الزام C2PA) در پلتفرم می‌ماند و برچسب **«ماژول پلتفرمی»** می‌خورد (بدون کد سندی). داده و قابلیت، دارایی کارفرماست؛ پس‌گردانی حذف نداریم.
۲) **شماره‌گذاری v14 مبنای برچسب‌های کاربر-رو می‌شود** (F13=مرجعیت، F14=سرمایه‌گذار، F15=نقش، F16=ورود به بازار، F17=بین‌المللی)، اما کلیدهای API و نام فیلدها (مثل `ownerRole`) برای سازگاری عقبنما دست نمی‌خورند — فقط labelهای فارسی و رشته‌های سندی عوض می‌شوند.
۳) **مهاجرت‌های داده per-tenant با نشان نسخه**: ردیف‌های persisted قدیمی (چارت، dossiers، عموم‌ها) با الگوی اثبات‌شدهٔ گام‌های ۵.۲/۵.۳/۵.۴ (ردیف بدون نشان نسخه → بذر مجدد) ارتقا می‌یابند؛ اجرای دوم باتری‌ها روی DB آلوده هم باید سبز بماند.

## ۵) اصول ثابت (در تمام گام‌ها)

- سه تصمیم مالک پابرجا: **بدون عدد دستی** (همهٔ اعداد از داده محاسبه شوند) · **فارسی + lt()/t()** (هر رشتهٔ کاربر-رو از دیکشنری EN عبور کند) · **tsc + باتری سبز → تیک → کامیت**.
- هر endpoint جدید → چک‌های `scripts/api-tests.mjs`؛ هر صفحه/کامپوننت جدید → باتری e2e خودش + رعایت ui-consistency.
- مهاجرت داده با نشان نسخه؛ باتری‌ها باید روی DB با ردیف persisted قدیمی هم سبز بمانند (الگوی گام ۵.۲).
- تغییر جهان دمو (بذرها) در همان گام با انتظارات api-tests هم‌گام شود.
- قراردادهای نمای فاز ۱۰ پابرجا؛ قراردادهای جدید این برنامه:
  - `publicMemberView` شامل: `statusFa` (چهارگانه)، `awarenessFa`، `engagementFa`، `actionConstraint`، `networkEffect`، `trustedSource`، `message`، `evidence`، `channel`، `ownerRole`، `nextAction`، `reviewDue`
  - `internationalView` شامل: `statusFa`، `identityFa`، `legalFa`، `dataShareFa`، `linkFa`، `ddStatus` (از پروندهٔ متصل)، `ownerRole`، `dueAt`، `referralFa`، `outcomeFa`

- [ ] ۱۴.۲ قواعد اعتبارسنجی ۱۰.۶.۲/۱۰.۶.۳ (سمت سرور، همه با ۴۰۰ و پیام فارسی روشن):
